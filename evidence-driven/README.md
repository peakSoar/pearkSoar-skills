# Evidence Driven

`evidence-driven` 是一套证据驱动工程 Harness Skill，用于把长期 AI 协作开发收敛为可恢复、可审计、可验证的仓库工作流。

[技能指令](skills/evidence-driven/SKILL.md) ·[安装与调用](#安装与调用) · [操作流程](#操作流程) · [文档职责](#文档职责) · [完整结构生成](#完整结构生成)

## 用途与边界

适合建立或整理项目工作流、按阶段执行跨会话任务，以及审计计划、实现和验收是否一致。普通局部修复只需范围控制和相应验证，不必创建完整阶段体系。

它提供三种模式：

| 模式 | 输入 | 产出 |
| --- | --- | --- |
| 初始化或转换 | 仓库事实、用户目标、已有规范与计划 | 按实际需要整理的工作流与阶段合同 |
| 执行 | 已有工作流与明确任务 | 最小实现、实际验证、当前验收和接力 |
| 审计 | 计划、源码、测试与运行证据 | 按影响排序的问题、证据和责任归属 |

Skill 不替代用户指令或目标仓库的有效规则，不自动获得提交、推送、发布、清理真实数据等权限。项目技术栈、业务规则和真实操作边界由目标仓库决定。

## 安装与调用

本仓库中需要复制的实际技能目录是 [skills/evidence-driven/](skills/evidence-driven/)，不是外层 `evidence-driven/` 项目目录。保持技能目录内的文件完整：

- 用户级：复制到 `~/.agents/skills/evidence-driven/`。
- 仓库级：复制到 `<目标仓库>/.agents/skills/evidence-driven/`。

安装后可直接发送：

```text
使用 $evidence-driven 为当前仓库建立 AI 工程 Harness。
使用 $evidence-driven 按现有流程完成这个修改并验证。
使用 $evidence-driven 审计当前项目的工作流，只报告问题。
```

支持隐式调用的 agent 也可根据技能描述选择它。技能名称保持 `evidence-driven`，避免更新后失去原有调用入口。

## 操作流程

```text
恢复仓库事实 → 判断任务规模 → 冻结基线 → 追踪责任归属
→ 比较方案 → 建立验证 → 最小实现 → 验证与归因
→ 更新当前验收 → 回写状态与下一会话继续点
```

### 1. 恢复与分类

优先按项目已有恢复顺序读取。没有约定时，依次读取仓库指令、计划与唯一状态、当前接力、当前阶段合同，以及它引用的源码、测试和验证条目；需要最近执行证据时读取当前验收。无需每轮加载所有阶段和历史记录。

核对 HEAD、分支和预存修改，区分聊天摘要、文档目标和当前代码事实。局部、低风险、单会话任务按普通任务处理；跨会话、跨模块、重要边界变更或需要发布与人工操作的任务才考虑阶段化。

### 2. 从事实推导计划

开工前记录目标、允许修改范围、预存修改、证据缺口和验证计划。涉及真实系统时，按需记录运行版本、配置标识、任务或数据水位，确保新旧结果可区分。

沿数据或状态流追踪四个角色：

| 角色 | 要回答的问题 |
| --- | --- |
| producer（生产者） | 数据或状态从哪里产生？ |
| transition（转换环节） | 映射、聚合、过滤、队列、持久化等环节改变了什么？ |
| consumer（消费者） | 哪个环节真正消费结果并作出决定？ |
| owner（责任主体） | 哪个模块唯一拥有这条规则或状态？ |

按“已确认问题 → 目标不变量 → 候选方案 → 选择理由 → 责任阶段 → 退出条件”制定计划。不要用功能清单代替问题证据，也不要为了迎合旧文档修改正确的代码。

### 3. 实施与验证

改变行为时，先用 characterization 测试记录当前行为，再用目标失败测试说明它违反哪条契约。测试应使用中性、可复现的样例；不能把验收样例中的名称或固定值写成生产规则。纯文档和不改变行为的机械修改不必制造红灯。

按风险选择定向测试、受影响回归、必要全量测试、构建、静态与契约检查、真实产品验收。遵守项目必需门禁，验证充分后不无目的地扩大测试。

记录实际命令、退出码、时间、测试数量（适用时）和证据位置。静态门禁要能让违规返回失败，不能只打印命中数量却退出成功。失败、跳过和未执行必须分开说明。

### 4. 真实操作与结果归因

需要用户授权或操作时，先完成已授权的准备与自动验证，再写明精确目标、动作、运行版本、数据基线和预期结果。用户完成后优先按其提供的 ID 验收，否则按事前水位和时间定位本轮产物。不得混用旧结果或修改真实数据制造通过。

记录每项检查的实际结果：通过、失败或未运行。失败要写清影响、已找到的原因和下一步；环境原因与代码原因分开说明。仅有改进建议时记录为建议，不将其当作已发生的故障。是否完成取决于该项目的退出条件和实际证据。

### 5. 收尾与接力

阶段计划回答“准备怎么做”，当前验收回答“本轮实际发生了什么”。被推翻的假设、失败过程、方案偏差和重开原因应如实写入本轮验收，不得把过程美化为一次成功。

每轮整体更新当前验收，然后回写唯一状态与接力。退出条件未全部满足时不能标记完成；只执行用户授权的后续范围。

## 文档职责

以下是目标项目的默认结构；已有等价文档时沿用原路径，避免建立第二套权威。

| 文档 | 唯一职责 |
| --- | --- |
| `AGENTS.md` | 长期边界、恢复入口、owner、权限与工作区纪律 |
| `docs/改造计划与进度.md` | 问题基线、阶段依赖、唯一当前状态和重开状态 |
| `docs/当前阶段与下一步.md` | 最近继续点、约束与下一会话提示，不独立决定状态 |
| `docs/阶段/Sxx-*.md` | 单阶段目标、范围、方案、验证计划和退出条件 |
| `docs/验证规则.md` | 可复用验证口径、命令与失败处理 |
| `docs/验收/当前验收.md` | 最近一轮实际执行证据，每轮整体覆盖 |

**保留一份当前验收，历史由 Git 保存，不新增按阶段累积的 records 目录。** 写入验收不等于允许 agent 提交 Git；未提交的旧内容不会自动成为 Git 历史，版本保存遵循用户的提交安排。转换已有工作流时保留既有历史，迁移或删除历史需要用户授权。

## 证据等级与状态

| 证据等级 | 含义与使用边界 |
| --- | --- |
| `CONFIRMED` | 源码、测试、运行数据等交叉确认，可支持设计 |
| `CODE_CONFIRMED` | 源码或测试直接确认，可支持实现 |
| `DATA_CONFIRMED` | 本轮运行或数据直接确认，可支持诊断与验收 |
| `STRONG_INFERENCE` | 证据支持但缺直接闭环，只用于可逆验证 |
| `HYPOTHESIS` | 尚未核验，只用于调查 |

阶段状态只由计划文档维护：

```text
NOT_STARTED → IN_PROGRESS → DONE
IN_PROGRESS → HUMAN_ACTION_REQUIRED → IN_PROGRESS
IN_PROGRESS ↔ BLOCKED
DONE → REOPENED → IN_PROGRESS → DONE
```

实现失败保持 `IN_PROGRESS`；已复现的环境阻塞记为 `BLOCKED` 并写解除条件；等待必要人工动作记为 `HUMAN_ACTION_REQUIRED`。同一时刻只允许一个活动阶段或活动重开。

新证据推翻已完成结论时，重开最早责任阶段，记录原状态、当前阶段和后继基线；后继状态不能随意重置。已有项目的重开协议优先。已完成计划遇到新目标时，新增阶段或独立计划，不重写旧完成历史。

## 完整结构生成

生成器只使用 Python 标准库。先按 [SKILL.md 的解释器检查规则](skills/evidence-driven/SKILL.md#python-解释器检查)获取解释器绝对路径，保存为当前终端临时变量 `PYTHON_EXECUTABLE`，不额外检查版本。以下命令在本 README 所在目录运行。

PowerShell：

```powershell
& $PYTHON_EXECUTABLE skills/evidence-driven/scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称> --dry-run
& $PYTHON_EXECUTABLE skills/evidence-driven/scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称>
```

Bash/zsh：

```bash
"$PYTHON_EXECUTABLE" skills/evidence-driven/scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称> --dry-run
"$PYTHON_EXECUTABLE" skills/evidence-driven/scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称>
```

仅在用户明确要求完整结构时使用生成器。先检查预览的目标和文件计划，再执行生成；已有授权足够时无需重复确认。

脚本通过固定 manifest 生成上表六个文件（含一个 S00 阶段模板）。任一目标文件已存在时，默认在写入前停止。核对并决定保留原文件后，可加 `--keep-existing` 补齐缺项。脚本不覆盖已有文件，写入失败时回滚本轮创建的内容。

脚本只替换 `{{PROJECT_NAME}}`。其余占位符必须按仓库事实填写；脚本成功不代表 Harness 已定制完成。未要求完整结构时，只选择必要模板。

## 仓库定制与交付检查

填写前核验平台、技术栈、模块责任、持久化、数据保留、生成契约、独占资源、并发、敏感信息、验证命令及外部副作用。只留下会改变实际决策的规则；项目专属事实留在目标仓库。

交付前检查：

- 状态表与机器可读状态一致，接力与验收没有形成第二权威。
- 链接和命令入口存在；生成结果无未解释占位符。
- 失败有责任归属和下一步，当前验收未沿用旧测试数字。
- 验收不含密钥、凭据和敏感载荷；真实系统证据按项目要求脱敏。
- 差异未超范围，用户预存修改得到保留。
- 说明实际验证、最终状态、未运行项和剩余风险。
