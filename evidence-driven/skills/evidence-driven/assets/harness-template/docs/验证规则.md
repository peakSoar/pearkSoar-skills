# {{PROJECT_NAME}} 验证规则

## 1. 适用范围

本文提供所有阶段共享的验证口径。阶段文件只选择需要执行的条目，实际结果写入《当前验收》，每轮整体覆盖，历史由 Git 保存。

## 2. 开工冻结

阶段开始或跨会话恢复时至少记录：

```powershell
git rev-parse HEAD
git status --short --branch
```

同时确认目标 HEAD、预存工作区、允许范围、当前阶段、已确认事实和验证计划。普通任务不必建立阶段，但仍须保护用户修改。

## 3. 自动验证层次

按风险从小到大执行：

1. characterization fixture；
2. 目标红灯；
3. 修改后的定向测试；
4. 受影响模块回归；
5. 相关完整测试；
6. lint、格式、类型和契约检查；
7. `git diff --check`；
8. 必要的真实产品验收；
9. 覆盖《当前验收》，阶段退出或反馈回流。

项目命令：

```text
{{TARGETED_TEST_COMMANDS}}
{{REGRESSION_COMMANDS}}
{{STATIC_AND_CONTRACT_COMMANDS}}
{{REAL_PRODUCT_VALIDATION_COMMANDS}}
git diff --check
```

环境失败与代码失败必须分开记录，不得把未执行或环境阻塞记为通过。

## 4. Characterization 和目标红灯

Characterization 只回答“旧实现现在做什么”，目标红灯回答“为什么该行为违反目标契约”。两者不得混为一条断言。

红灯使用合成、中性 fixture，定位 producer、transition、consumer 和 owner；修改前稳定失败，修改后通过，并由相邻回归保护未改行为。纯文档或无生产行为的机械修改可以不制造红灯，但须在验收中说明。

## 5. 事实等级

| 等级 | 证据要求 | 使用边界 |
| --- | --- | --- |
| `CONFIRMED` | 源码、测试、运行数据等多类证据交叉一致 | 可以驱动设计 |
| `CODE_CONFIRMED` | 当前源码或测试直接确认 | 可以驱动生产实现 |
| `DATA_CONFIRMED` | 数据库、日志或运行产物直接确认 | 可以驱动问题归因和验收 |
| `STRONG_INFERENCE` | 多项证据支持但缺一个直接闭环 | 只能驱动可逆验证 |
| `HYPOTHESIS` | 尚未完成核验 | 不得驱动长期或不可逆实现 |

## 6. 阶段状态边界

状态权威只在《改造计划与进度》；接力和验收只投影当前事实。

| 状态 | 进入边界 | 状态内行为 | 退出边界 |
| --- | --- | --- | --- |
| `NOT_STARTED` | 阶段合同完整且无其他活动阶段 | 只做开工审计和补充证据 | 冻结基线后进入 `IN_PROGRESS` |
| `IN_PROGRESS` | 开工冻结完成或阻塞解除 | 实施并按反馈链验证 | 通过、等待用户或外部阻塞时分别流转 |
| `HUMAN_ACTION_REQUIRED` | 自动工作完成，只剩用户授权或真实操作 | 等待并保护基线 | 用户提供结果后回到 `IN_PROGRESS` 只读验收 |
| `BLOCKED` | 阻塞已复现并记录解除条件 | 保存证据，不绕过阻塞 | 条件发生可验证变化后回到 `IN_PROGRESS` |
| `DONE` | 退出条件全部满足且实际验收通过 | 作为后续基线 | 新证据推翻结论时进入 `REOPENED` |
| `REOPENED` | 新证据推翻已完成 owner | 定位最早责任阶段和影响范围 | 进入 `IN_PROGRESS` 返工 |

实现失败留在 `IN_PROGRESS`；环境阻塞进入 `BLOCKED`；需要用户操作进入 `HUMAN_ACTION_REQUIRED`；新证据推翻已完成 owner 时进入 `REOPENED`。

## 7. 人工操作矩阵

| 操作 | AI 可否执行 | 前置要求 | 完成后 |
| --- | --- | --- | --- |
| 测试、lint、typecheck、契约检查 | 可以 | 明确范围并保护工作区 | 记录命令和结果 |
| 真实产品只读检查 | 按项目规则 | 不下载、不重置、不修改真实数据 | 记录版本、动作和结论 |
| 构建、下载工具、重置环境、清理真实数据 | 默认不可以 | 用户明确授权并确认目标与影响 | 回到 `IN_PROGRESS` 只读验收 |
| 新增依赖 | 默认不可以 | 说明必要性、维护状态、许可证、锁定版本和替代方案 | 更新锁文件并验证供应链 |
| 发布、部署、push、创建 PR | 默认不可以 | 用户明确要求 | 记录外部结果 |

## 8. 本轮证据

逐项记录实际检查结果、失败原因和未运行项。环境失败与代码失败分开说明；未执行或证据不足不能记为通过。仅有改进建议时如实记录，是否阻塞完成由项目明确的退出条件决定。

真实操作前按需记录版本、配置标识、目标、任务或数据水位和预期结果；操作后优先用用户提供的 ID，否则按事前水位和时间定位本轮产物。不得混用旧结果或修改真实数据制造通过。证据遵循项目敏感信息边界。

静态门禁须能让新增违规返回失败；不得仅打印统计而始终退出成功。验收保留被推翻的假设、实际失败、方案偏差和责任归属，不改写成与计划完全一致。

## 9. 当前验收与收工

`docs/验收/` 只保留一个 `当前验收.md`。每轮整体覆盖并记录：目标 HEAD、工作区、任务范围、预存修改、本轮修改、实际命令与结果、状态变化、未运行项和剩余风险。

敏感信息不得进入验收。历史测试数字不能计入本轮验证。

收工前确认相关测试和门禁完成、`git diff --check` 通过、差异未越界、用户修改未被清理、状态与验收一致。只有全部退出条件满足后才能把阶段设为 `DONE`；阶段完成后不自动进入下一阶段。
