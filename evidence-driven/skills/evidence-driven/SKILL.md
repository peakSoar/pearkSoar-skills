# 证据驱动工程 Harness

将工程任务组织为“事实 → 计划 → 实施 → 验证 → 状态与接力”。

## Python 解释器检查

首次运行本技能的 Python 脚本前，按顺序检查用户已有的解释器：

```text
python -c "import sys; print(sys.executable)"
python3 -c "import sys; print(sys.executable)"
```

使用第一条成功返回的解释器绝对路径；第一条失败时再检查第二条，不额外检查版本。

将选中的路径保存为当前终端的临时变量 `PYTHON_EXECUTABLE`，后续本技能脚本统一用该路径运行，不修改系统或用户的永久环境变量。变量不一定跨工具调用保留；新终端中需重新设置已确认的路径。

两条命令都无法找到可用解释器时，回复 **没有python依赖**。停止运行依赖该解释器的脚本，不自行安装或升级 Python。仅阅读、规划和文档审计无需 Python，可继续执行。

## 先恢复，再决定范围

遵循用户指令和目标仓库的有效规则，以源码、测试和本轮运行证据校正文档与聊天摘要。保留项目已有的技术边界与用户修改，不机械覆盖现有 Harness。

按项目恢复顺序读取；没有约定时使用：仓库指令 → 计划与唯一状态 → 当前接力 → 当前阶段合同 → 合同引用的源码、测试和验证条目；需要最近执行证据时读当前验收。核对 HEAD、分支和工作区，不默认加载全部历史。

先选模式：建立或整理工作流用“初始化/转换”；按已有流程做任务用“执行”；检查一致性用“审计”。局部、低风险、单会话任务不创建阶段；跨会话、跨模块、重要边界变更或需要发布及人工操作时才考虑阶段化。

“要不要阶段化”和“文档要不要完整”是两个独立判断。任务可以小到不需要新阶段，但已经建立的 Harness 文档仍按完整结构维护，不能因为本次任务简单就把文档裁薄。

## 文档职责

沿用目标仓库等价文件；新建时使用 `assets/harness-template/` 下的模板：

| 文件 | 唯一职责 |
| --- | --- |
| `AGENTS.md` | 长期边界、owner、恢复入口、权限和工作区规则 |
| `docs/改造计划与进度.md` | 问题基线、依赖、唯一当前阶段及重开状态 |
| `docs/当前阶段与下一步.md` | 最近继续点与下一会话提示 |
| `docs/阶段/Sxx-*.md` | 本阶段目标、允许范围、方案和退出条件 |
| `docs/验证规则.md` | 复用验证口径与反馈规则 |
| `docs/验收/当前验收.md` | 最近一轮实际执行证据，每轮整体覆盖 |

每份文件的章节结构以模板为准。不得合并章节、不得省略“看起来用不上”的章节、不得把两节合成一段概述。模板里某节确实不适用于当前项目时，保留标题写“不适用”并说明原因，让缺失可见，而不是悄悄删掉。

阶段合同记录计划，当前验收记录事实与偏差，不用复选框替代状态或证据。不新建累积式 records 目录；历史由 Git 保存，但写文档不授权提交。未提交内容不会自动留存 Git 历史，遵循用户的版本保存安排；已有历史不擅自迁移或删除。

## 生成完整结构（默认路径）

初始化/转换模式默认产出完整结构。用户说“建立开发流程”“整理一下项目文档”“搞个阶段计划”都算，不需要他说出“完整”两个字。

1. 检查项目指令、架构、模块 owner、数据保留、契约源、资源与并发、敏感信息、验证入口、Git 状态和外部操作边界，区分已有事实与目标设计。

2. 先读模板的六个文件，逐节确认每个章节在当前项目里对应什么。读模板不是可选步骤，是填写的依据。

3. 用临时变量中的解释器运行生成器，把完整结构落到目标仓库：

   powershell:

   ~~~powershell
   & $PYTHON_EXECUTABLE scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称> --dry-run
   ~~~

   bash/zsh:

   ~~~bash
   $PYTHON_EXECUTABLE  scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称> --dry-run
   ~~~

4. 生成器遇已有目标文件默认零写入。核对并保留原文件后才使用 `--keep-existing` 补齐缺项；不得覆盖。已有授权足够时不重复请求确认。

5. 已有等价文档时不重新生成，改为逐节对照模板补齐缺失章节，在原位置补，不建第二套。

6. 用确认的项目事实填写全部 `{{...}}` 占位符，按下一节的填写标准写。无法确认的标记为证据缺口。生成成功不等于定制完成。

### 精简模式（仅在用户明确要求时）

只有用户说出“最简”“轻量”“只要能跑”“先建必要的就行”“不用这么全”这类明确要求，才允许裁剪。裁剪时：

1. 先产出完整结构，再删，不要一上手就只写几节。
2. 在《当前验收》列出删掉的文件和章节，以及为什么当前项目用不上。
3. 保留的章节不得再压缩内容，不能因为文件变少就把剩下的写成概述。

用户没有明确要求精简时，任何“这个项目还简单，先简版”的自行判断都不成立。

## 填写标准

占位符和正文都要写成可判定的事实。一条合格的填写同时具备三项：

- **主语**：谁拥有、哪个模块、哪个类、哪个角色。
- **位置**：文件、类、方法、行号、端口、键名、表名、命令中的至少一项。
- **可观察结果**：能被运行或检查的东西——退出码、状态码、字段值、行数、键的 TTL、某个方法的返回值。

以下词在本文档体系里没有判定标准，禁止单独充当结论：统一、完善、优化、规范、合理、适当、相应、相关、进一步、更好地、加强、提升。需要表达这类意思时，写出具体做了什么、在哪、结果如何。

对照样例见 `assets/examples/fill-samples.md`，五组不合格与合格的写法对比，外加三段填好的片段。填写时先看样例，再动笔。

无法确认的内容写“证据缺口：<未确认的事实>，需要 <哪个动作或数据> 才能确认”，不要用抽象句掩盖未核实。不确定但影响设计的写 `HYPOTHESIS` 并给出验证方式。

占位符填不出具体事实，说明这一节在当前项目还不成立。这种情况保留章节标题、写“待定：<缺什么>”，并在验收的未运行项里记一笔，而不是删掉或写成空话。

## 执行

1. 冻结 HEAD、分支、预存修改、允许范围、事实、证据缺口和验证计划。真实系统任务按需记录运行版本、配置标识和数据水位，保护敏感信息。
2. 追踪 producer（产生数据）、transition（转换数据）、consumer（消费并决策）和唯一 owner；区分代码原因、数据现象和环境失败。发现旧测试固化错误时先说明契约。
3. 行为修改先建立 characterization（当前行为）和目标失败测试（违反的契约），使用中性 fixture。纯文档、注释和无行为机械改动可免红灯；项目允许的其他例外记录理由。
4. 最小实现后执行定向测试、受影响回归和必要门禁。全量测试、构建和真实验收按项目要求与风险选择，充分验证后停止扩大范围。
5. 每项失败记录根因、责任归属和下一步；不能删除断言、篡改样例、跳过失败、硬编码业务样例或修补真实数据来制造通过。
6. 必要人工动作前完成已授权准备，列出目标、动作、版本、水位和预期结果。用户完成后按提供的 ID 或事前水位只读验收本轮产物，不混用历史结果。
7. 整体更新当前验收，再回写状态与接力。普通任务不改已完成阶段状态；继续后续工作须在用户授权范围内。

## 证据、结果与状态

关键结论标记证据等级：
- `CONFIRMED`：多类证据交叉一致。
- `CODE_CONFIRMED`：源码或测试直接确认。
- `DATA_CONFIRMED`：本轮运行或数据直接确认。
- `STRONG_INFERENCE`：有支持但缺直接闭环，只驱动可逆验证。
- `HYPOTHESIS`：待核验，只驱动调查，不驱动长期或不可逆设计。

检查结果按实际情况记录为通过、失败或未运行。失败说明影响、原因和下一步；环境阻塞与代码问题分开说明。仅有改进建议时如实记录，不作为已发生故障。任务是否完成按目标仓库的退出条件和实际证据判断。

阶段状态只有一处维护：
- `NOT_STARTED → IN_PROGRESS → DONE`：退出条件和必要验收全部满足才能完成。
- 实现或回归失败保持 `IN_PROGRESS`。
- 已复现的环境或权限阻塞进入 `BLOCKED`，写明解除条件。
- 需要必要人工动作进入 `HUMAN_ACTION_REQUIRED`；完成后回到 `IN_PROGRESS` 验收。
- 新证据推翻已完成 owner 时 `DONE → REOPENED → IN_PROGRESS`，重开最早责任阶段，记录原状态、恢复点和后继基线；不得在后继阶段复制临时修复。
- 同时只有一个活动阶段或活动重开；遵循项目已有重开协议，已完成计划的新需求新建阶段或计划，不重置旧状态。

## 交付断言

生成、转换或整体更新文档后，逐条核对。任何一条不通过，不得报告完成，也不得把“已生成”当成“已交付”。

| 断言 | 检查方式 |
| --- | --- |
| 无遗留占位符 | `grep -rn "{{" <目标> --include=*.md` 零命中，保留的说明性占位符须在验收里点名 |
| 章节与模板一致 | `AGENTS.md` 与阶段、验收、验证规则文件的章节数、标题逐条对齐模板；缺失章节在验收写明理由和用户确认 |
| 接力五栏齐全 | 当前状态、最近完成、当前继续点、必须保留的边界、下一会话提示五栏都在 |
| 最近完成不超上限 | 每条带 `YYYY-MM-DD`；当天条目全留；总数不超过 5 条 |
| 状态四处一致 | 计划正文、JSON 块、接力、当前验收中的阶段与状态完全相同，且只有一个活动阶段或活动重开 |
| 基线与退出条件可判定 | 问题基线每行有责任阶段，每个阶段有退出条件，条件是可以判断真假的事实而不是形容词 |
| 引用可解析 | 文档间相对链接指向真实文件，代码块成对闭合 |
| 范围未越界 | `git status --short` 的改动落在允许范围内，预存用户修改未被覆盖 |
| 敏感信息 | 验收不含密钥、凭据、Token、`Authorization`、真实密码与业务载荷 |

## 审计

审计时对照状态、合同、接力、当前验收、源码和测试，检查重复权威、重复 owner、旧验证结论、未处理失败、权限扩大、失效链接和敏感内容。仅要求审计时报告问题，不改文件。

当前验收须包含开始/结束 HEAD 或工作区标识、范围、预存与实际修改、事实和被推翻假设、实际命令/时间/退出码/适用的测试数量、必要真实操作证据、偏差、检查结果、状态变化、未运行项、剩余风险与下一步。不能沿用历史测试数字或改写事实迎合计划。

提交、推送及其他外部操作遵循用户授权。
