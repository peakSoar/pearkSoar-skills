# 设计说明

## 目标

本 Skill 解决长期 AI 工程协作中的四类问题：聊天摘要与仓库事实冲突、多份状态权威漂移、跨层重复业务 owner，以及“代码写完即完成”导致的验证断链。

## 核心结构

```text
仓库事实
-> 固定恢复
-> 任务分级
-> 开工冻结
-> producer / transition / consumer / owner 审计
-> characterization 与目标红灯
-> 最小实现
-> 分层验证
-> 验收和状态回流
-> 跨会话接力
```

## 渐进披露

Codex 首先只读取 Skill 的 `name` 和 `description`；选择 Skill 后读取 `SKILL.md`；只有进入对应模式时才读取 `references/`，需要生成 Harness 时才使用 `assets/`。

这种结构让触发信息保持简短，同时避免在普通任务中加载完整工作流和模板。

## 确定性完整生成

“完整结构”具有明确、重复的文件集合，因此由 `scripts/scaffold_harness.py` 和固定 manifest 拥有。脚本先验证模板清单和目标冲突，再创建全部缺失文件；默认不覆盖，失败时回滚本轮已创建内容。

按需初始化仍由 Skill 根据仓库事实选择最少必要资产。脚本只拥有完整结构的机械生成，不拥有项目 owner、架构边界或模板占位符的语义判断。

## 三种模式为何属于一个 Skill

初始化、执行和审计共享同一组证据等级、owner 规则、状态机和权限边界。拆成多个 Skill 会重复这些不变量，并可能在同一请求中产生多个竞争入口，因此使用一个入口按模式路由。

## 通用与项目专属边界

通用 Skill 只拥有恢复方法、证据分级、状态反馈、owner 审计和模板选择规则。技术栈、模块 owner、敏感数据、验证命令、发布方式和真实操作权限必须由目标仓库拥有。

## 非目标

- 不替代目标仓库的 `AGENTS.md` 或用户指令；
- 不为普通局部任务强制建立阶段；
- 不自动获得构建、发布、清理数据或其他高影响操作权限；
- 不把一次项目事故扩展为所有仓库的永久规则；
- 不维护当前验收的累积历史，历史由 Git 保存。
