# 证据驱动工程 Harness

建立或应用仓库内生工作流，使 AI 工程任务能够跨会话恢复、以证据为基础、严格控制范围并完成验证闭环。

## 保护既有权威

行动前先检查目标仓库。已有 `AGENTS.md`、用户指令、源码事实、测试、Git 状态和授权边界均高于本 Skill 及其模板。

不得机械覆盖已有 Harness。先识别每项决策的当前权威，保留有效的项目专属规则，并且只处理用户要求的范围。不得把目标架构描述为已经确认的事实。

## 选择模式

### 初始化或转换

适用于创建 Harness，或将已有工作流文档转换为 Harness。

1. 阅读 [工作流模型](references/workflow-model.md) 和 [仓库定制](references/customization.md)。
2. 检查仓库指令、架构、测试、验证命令、敏感数据边界、Git 状态和外部副作用。
3. 判断任务需要完整阶段 Harness，还是轻量任务协议；普通局部任务不得创建阶段。
4. 用户明确要求“完整结构”“完整 Harness”或“生成全部 Harness 文件”时，必须先执行 `scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称> --dry-run`，确认计划后再去掉 `--dry-run` 执行；不得手工重建完整目录。
5. 完整生成遇到已有 manifest 文件时默认停止且零写入。只有核对现有文件并决定保留后，才可使用 `--keep-existing` 创建缺失文件；不得用脚本覆盖已有文件。
6. 用户没有明确要求完整结构时，从 `assets/harness-template/` 选取最少必要文件；已有同类文件时合并职责，不直接替换。
7. 使用已确认的仓库事实替换所有 `{{...}}`；无法确认时记录证据缺口，不得猜测。
8. 建立唯一阶段状态权威、一个当前接力、复用验证规则、阶段合同和覆盖式当前验收。
9. 检查链接、状态一致性、残留占位符、敏感内容、差异范围和工作区保护。

### 执行

适用于用户明确要求通过本 Harness 执行工作。

1. 遵循仓库自己的恢复顺序；没有既有顺序时使用[工作流模型](references/workflow-model.md)。
2. 根据持续时间、模块跨度、风险、发布影响和所需人工操作，将请求划分为普通任务或阶段任务。
3. 修改生产代码前冻结 HEAD、分支、预存修改、允许范围、已确认事实、证据缺口和验证计划。
4. 追踪相关 producer、transition、consumer 和唯一 owner，区分数据现象、环境失败和代码原因。
5. 行为修改先建立 characterization 覆盖和目标不变量红灯；仓库合同允许例外时必须记录理由。
6. 从定向检查逐步扩大验证范围，并将每项失败路由到明确状态或下一步。
7. 只更新本任务拥有的文档；普通任务不得修改已完成阶段状态。

### 审计

适用于检查已有 Harness 是否一致、可靠或可复用。

1. 阅读[工作流模型](references/workflow-model.md)。
2. 对照源码、测试、Git 状态、接力、阶段合同和当前验收检查声明状态。
3. 检查多重权威、重复 owner、过期测试结论、悬空失败、权限过宽、验收累积和敏感数据泄漏。
4. 按影响和证据等级报告问题；用户未要求修改时不得重写文件。

## 不可违反的不变量

- 仓库事实高于聊天摘要和模板默认值。
- 同一规则、状态、序列化行为或生命周期只有一个 owner。
- `HYPOTHESIS` 只能驱动可逆调查，不能驱动长期或不可逆设计。
- characterization 描述当前行为，目标红灯表达尚未满足的契约。
- 失败或未执行的检查不得报告为通过。
- 当仓库或用户规则要求时，破坏性、外部、发布、凭据、真实数据或依赖变更操作必须在实际执行前取得明确授权。
- 保护用户预存修改，不把无关问题混入当前差异。
- 验收历史由 Git 保存；《当前验收》只记录最近一轮实际证据。

## 交付要求

说明使用的模式、发现的权威和证据、修改文件、实际运行检查、最终任务或阶段状态及未解决风险。项目专属事实必须留在目标仓库中，不得写入本通用 Skill。
